# Homebrew のビルドの来歴とコード署名 {#build-provenance-and-code-signing-for-homebrew}

著者: [William Woodruff](https://github.com/woodruffw), [Dustin Ingram](https://github.com/di)
最終更新: 2023 年 7 月

## 概要 {#summary}

この文書は、パッケージマネージャーの Homebrew に、ビルドの来歴（プロベナンス、build provenance）と暗号学的な署名を導入するための技術的な提案です。最終的な目標は、Homebrew の真正性とサプライチェーンの完全性を高めることです。具体的には、あるパッケージが、証明（アテステーション、attestation）のあるソース成果物からビルドされたこと、そしてアテステーションのあるマシン（つまり、Homebrew が管理する GitHub Actions のワークフロー）でビルドされたことの両方を確かめられるようにします。

この提案は、個々の技術項目に分かれています。それぞれは、ある程度独立した作業単位になるように意図しています。作業単位は依存関係の順に並んでいます。つまり、クライアント側で署名を検証できるようになる前に、署名の生成が済んでいなければなりません。

## 技術的な背景 {#technical-background}

[Homebrew](https://brew.sh/) は macOS で最も広く使われているパッケージマネージャーで、1 日あたり数百万人のユーザーと、[数百人の活動中のコントリビューター](https://github.com/Homebrew/brew/graphs/contributors)がいます。Homebrew は Ruby で書かれており、GitHub Actions を使って、人気のあるオープンソースプロジェクトのバイナリパッケージ（「[ボトル（bottle）](https://docs.brew.sh/Bottles)」と呼ばれます）を作ります。クライアントはそれを、`brew` CLI を通じて自分のマシンにインストールします。Homebrew は毎年、オープンソースパッケージのバイナリビルドを [4 億件以上](https://formulae.brew.sh/analytics/install/365d/)、macOS のユーザーに届けています。

[Sigstore](https://www.sigstore.dev/) は、コード署名を誰でも利用できるようにすることを目指す Linux Foundation のプロジェクトです。オープンな標準（OpenID Connect、WebPKI、Certificate Transparency）を組み合わせて、暗号によらないアイデンティティ（メールアドレスや GitHub Actions のワークフローのアイデンティティなど）を短命の署名鍵に結び付けます。その鍵は、`gpg` やほかの署名ツールとほぼ同じように、成果物への署名に使えます。

[SLSA](https://slsa.dev) は、サプライチェーンセキュリティのための、段階的に導入できる一連の指針です。業界の合意によって定められており、これらのベストプラクティスを使っていることを検証可能な形で証明するための仕様でもあります。SLSA が定める仕様は、ソフトウェアの作り手と使い手の両方に役立ちます。作り手は SLSA の指針に従うことでソフトウェアのサプライチェーンをより安全にでき、使い手は SLSA を使って、あるソフトウェアパッケージを信頼するかどうかを判断できます。

## 技術項目 {#technical-items}

### Homebrew 公式の tap に対する来歴のアテステーションと署名 {#provenance-attestations-and-signatures-for-official-homebrew-taps}

Homebrew のパッケージ作成の工程は、GitHub Actions を中心に組み立てられています。とくに Homebrew は GitHub Actions を使って、すべてのコアの formula（LLVM、`bash`、`git` のようなパッケージの仕様）をボトル（クライアントのマシンにインストールできるバイナリの配布物で、`.app` や `.pkg` に似ています）へビルドします。ボトルはその後 GitHub Packages（サードパーティの tap の場合はほかのホスト）で配布され、エンドユーザーのクライアントによって、たとえば `brew install` の実行時にインストールされます。

Homebrew は `homebrew-core` のすべてのビルドに GitHub Actions を使っているので、Homebrew の CI は、GitHub Actions が[その場で提供する OpenID Connect のアイデンティティ](https://docs.github.com/en/actions/deployment/security-hardening-your-deployments/about-security-hardening-with-openid-connect)をごく簡単に利用できます。これらのアイデンティティは、ビルドの来歴の生成と Sigstore による署名に使えます。つまり、Homebrew の既存の CI ワークフローは、比較的わずかな追加の設定だけで（そして外部での鍵管理はまったくなしで）、ボトルのビルドごとに、有効な in-toto のアテステーションと Sigstore の署名を生成できることになります。

ボトルへの署名のおおまかな流れは次のとおりです。

1. ボトルをビルドする既存のワークフローに、署名のステップを加えます。このステップは、`master` に載るボトル（つまり、通常の PR の流れの一部としてビルドされる一時的なボトルではないもの）に対する仕上げのステップとしてだけ実行されます。

2. 署名のステップは、ボトルについて*証明する*、Sigstore の署名付きのアテステーションを生成する責任を負います。この署名付きのアテステーションには、最低限、ボトルのアーカイブの SHA256 ダイジェストとボトルのファイル名を含めるべきです。ダイジェストは、その署名が特定のボトルの内容に対するものであることを示すために必要です。ファイル名は、その署名が特定のインストール手順に伴うよう意図されたものであることを示すために必要です（つまり、攻撃者が `foo` のボトルを、正しく署名された `bar` のボトルや、リゾルバーが出した結果とは異なるバージョンの `foo` のボトルにすり替えた場合に、`brew install foo` の検証が通ってはなりません）。アテステーションの正確な形式は、今後の技術的な検討によって決まります。現在の候補には、[in-toto の来歴のアテステーション形式](https://slsa.dev/provenance/v1)（SLSA v1.0 向けに設計されたもの）、[in-toto の VSA のアテステーション形式](https://slsa.dev/verification_summary/v1)（同じく SLSA v1.0 向けに設計されたもの）、そして [NPM のアテステーション形式](https://github.com/npm/attestation/tree/main/specs/publish/v0.1)を応用したものがあります。どの形式を選ぶにしても、最終的なアテステーションは [SLSA のアテステーションモデル](https://slsa.dev/attestation-model)に沿ったものになります。

3. 署名のステップは、できあがった署名を、ボトルと同じオブジェクトストレージへアップロードする責任を負います。また、アップロードした署名の場所を、formula とボトル自身のメタデータだけから、予測可能で誰でも導き出せる方法で特定できるようにする責任も負います。これは、[来歴の配布についての SLSA の指針に沿ったもの](https://slsa.dev/spec/v1.0/distributing-provenance)です。言い換えると、ボトルのリソースへのアクセス方法を知っているクライアントは、追加のメタデータなしで、ボトルの署名のリソースにもアクセスできるべきです。これは、Sigstore でコンテナーイメージに署名するときの[署名の場所と管理](https://docs.sigstore.dev/cosign/signing_with_containers/#signature-location-and-management)の仕組みに似ています。

この流れが終わると、ボトルと、その署名付きのアテステーションの両方が、tap に対応するオブジェクトストレージに置かれているはずです。

ボトルが作られるたびに署名するのに加えて、署名のステップは、既存のボトルの署名（と対応するアテステーション）を「バックフィル」（さかのぼって補うこと）するのにも使えます。これらの署名は、ビルドの来歴の保証というより、実質的には既存のボトルに対する公証として働きます。この「バックフィル」の段階では、既存のすべてのボトルについて最初のアテステーションと署名を生成することを想定しています。その後、この段階は取り除かれ、ボトルをビルドするワークフローのなかでの署名に置き換えられます。最初のバックフィルの作業のあとで「バックフィル」の機能を取り除くことで、それ以降のすべてのアテステーションに、対応するビルドの来歴があることが保証されます。

tap に対する署名がすべて済んだら（つまり、参照されているすべてのボトルに「バックフィル」またはビルドのアテステーションのどちらかがある状態になったら）、その tap は「フラグデー（flag day）」のメタデータを定めなければなりません。tap はタイムスタンプ `T` を指定するべきであり、それ以降、その tap の formula が定義するすべてのボトルは署名されています。このためには、tap 自身が自分のフラグデーについて正直であることが根本的に必要です。tap のフラグデーを書き換えられる攻撃者は、署名の検証を無効にしてダウングレードを行えます。これは、攻撃者に tap のファイルを変更させてはならないという Homebrew の既存の脅威モデルと、対象の範囲は変わりません。言い換えると、この署名の仕組みが守るのはボトルそのものだけで、tap のリポジトリは守りません。tap のリポジトリは、引き続き方針として保護しなければなりません。

### サードパーティの tap に対する Sigstore の署名 {#sigstore-signatures-for-third-party-taps}

この提案の範囲には含まれませんが、この取り組みによって、独立したオープンソースの団体や企業が保守しているようなサードパーティの tap でも、署名ができるようになります。

GitHub でホストされているサードパーティの tap では、署名の流れはまったく同じになります。ボトルをビルドするどのワークフローでも（公式のワークフローを再利用する場合も含めて）、ボトルに署名することになります。

## Homebrew でのクライアント側の署名検証 {#client-side-signature-verification-in-homebrew}

上で説明した Sigstore の署名は、通常の `brew install` の流れのなかでクライアントが検証できるように、それぞれの tap のオブジェクトストレージへ送られます。

Sigstore の署名を検証するには、個々の `brew` クライアントに次のものが必要です。

- 信頼の根拠（trust proposition）、つまり、署名を生成するアイデンティティを信頼する理由。Homebrew の場合、この信頼の根拠は tap 自身のアイデンティティから来ます。`brew tap foo/bar` を実行するという行為によって、`github.com/foo/bar` に結び付いた Sigstore のアイデンティティを、その tap のボトルに署名するものとして信頼できることが確立されます。これは暗黙の `brew tap` の実行にも当てはまります。たとえば `brew install foo/bar/baz` は、ユーザーが `baz` に、`foo/bar` という GitHub のアイデンティティによる署名があると期待していることを表明します。
    - 単純にするために、この提案では、tap のアイデンティティを GitHub Actions のアイデンティティだけに限ります。これらは tap そのものに「もともと備わっている」ので、ユーザーが信頼について追加の判断をする必要がないからです。この仕組みを将来拡張するときには、tap のアイデンティティを、メールアドレス、ユーザー、あるいは Sigstore が対応しているほかの種類のアイデンティティにまで広げることもありえます。
- Sigstore の署名を検証できる Sigstore のクライアントライブラリ。

クライアント側でボトルを検証するには、どのボトルが実際に署名されているのかを `brew` が知っている必要があります。クライアントは、これを確かめるために上記の「フラグデー」のメタデータを使うべきです。`brew install` は、フラグデーがあり、*かつ*そのフラグデーがローカルのシステム時刻より前である tap については、署名のないボトルのインストールをいっさい拒否するべきです。

ボトルの署名検証のおおまかな流れは、tap を追加する時点では次のとおりです。

- ユーザーが明示的な tap（`brew tap foo/bar`）か暗黙の tap（`brew install foo/bar/baz`）のどちらかを行い、ローカルの `brew` クライアントはその操作にもとづいて信頼の根拠を確立します（「`foo/bar` のボトルは、`foo/bar` のアイデンティティによって署名されていなければならない」）。
- ローカルの `brew` クライアントは「フラグデー」のメタデータを探します。それが存在し、ローカルのシステム時刻より前であれば、その tap が参照するすべてのボトルについて署名の検証を強制します。

そして、`brew install` の時点では次のとおりです。

- `brew install` の実行中に解決されたそれぞれのボトルには、付随する署名がなければなりません。付随する署名がなければ、`brew install` は失敗しなければなりません。

- `brew install` は、それぞれのボトルと署名について、上の署名の工程で説明した*アテステーション*を信頼できることを確かめなければなりません（アテステーションの該当するフィールドを確認するか、独立して導き出したメタデータからアテステーションを丸ごと再構成するかのどちらかによります）。これが、署名検証の平文の入力として使われます。この入力は、対応する署名とともに、下層の Sigstore クライアントへ渡されます。Sigstore クライアントは、署名の検証と、それに伴うアイデンティティの検証の両方を行う責任を負います。

- 下層の署名検証が失敗した場合、`brew install` は失敗しなければなりません。

これまでの Homebrew の機能と同じように、署名検証は、既定で有効になる前に、機能フラグで切り替える実験的な形で取り込まれ、有効にされることがあります。ボトルが署名付きで少しずつ更新／再ビルドされている間、検証は任意です。コアのボトルがすべて署名されたら、フラグデー以降はすべてが署名されていなければなりません。

## Homebrew のソースとビルドの完全な来歴 {#full-source-and-build-provenance-for-homebrew}

ボトルへの署名とその後の検証によって、次の段階の改善も可能になります。Homebrew はソースからビルドしてボトルを作るので、そのソース成果物の署名を検証することも考えられます。そして、その署名に Homebrew 自身のボトルの署名で*副署*（countersign）すれば、（サードパーティのアップストリームが作った）元のソース成果物から、Homebrew が作ったバイナリ成果物までを結ぶ、暗号学的に強い結び付きを実質的に作り出せます。

それぞれの formula のソース成果物を検証するには、その成果物に署名するものとして信頼するアイデンティティについての追加のメタデータを、それぞれの formula が持つか、導き出す必要があります。やり方は、クライアント側の検証の節で説明した「信頼の根拠」に似ています。そのためには、Homebrew の formula の DSL を変更する必要があります。

このメタデータのための DSL の変更として*考えられる*一例を、下に示します。

```ruby
class Ripgrep < Formula
  desc "Search tool like grep and The Silver Searcher"
  homepage "https://github.com/BurntSushi/ripgrep"
  url "https://github.com/BurntSushi/ripgrep/archive/13.0.0.tar.gz"

  # OPTION 1:
  # verifies using the default `#{url}.sigstore` bundle above
  # with the identity and issuer for the repo
  sigstore :default

  # OPTION 2:
  # verifies using the provided bundle/identity/issuer
  sigstore do
    # specifies the signature's URL
    bundle "https://<...>.sigstore"
    # the expected signature identity, e.g. an email or GitHub slug
    identity "<...>"
    # (optionally) the expected OIDC issuer
    oidc_issuer "<...>"
  end
end
```

GitHub でホストされ、GitHub のリリースを通じて（署名とともに）提供されているソース成果物については、1 つ目の方法で十分です。Homebrew は、`url` の `user/repo` の部分から、期待される署名のアイデンティティを導き直せます。

ほかのサービスでホストされている（または、GitHub Actions 以外のアイデンティティで署名されている）ソース成果物については、2 つ目の方法によって、formula が署名の URL と対応するアイデンティティを明示的に指定できます。

検証可能なソース成果物を持つ formula については、上で説明した署名付きのボトルのアテステーションを拡張して、検証済みのソースの署名を含められます。その結果が副署になります。この副署は、上の項目で説明したのと同じ、基本的なクライアント側の署名検証の手順を使って、`brew` が（Sigstore クライアントを通じて）検証できます。そのため、これは「ボトルだけ」の署名に対する段階的な機能強化になります。

## 互換性についての考慮事項 {#compatibility-considerations}

### macOS の実行ファイルのコード署名 {#macos-executable-code-signing}

この提案が対象にするのはボトルだけで、そのなかの個々の実行ファイルは対象にしません。そのため、「アドホック（ad-hoc）」な実行ファイルの署名（真正性のためではなく、Apple Silicon 上の macOS がすべての実行ファイルに署名を求めるために生成されるもの）について、Homebrew の現在の使い方にも、将来の使い方にも影響しないはずです。

## 脅威モデル {#threat-model}

### 範囲 {#scope}

この提案の範囲は、Homebrew のボトルに対する*認証されたビルドの来歴*です。

*ソースの侵害*は、この提案の範囲に含まれ**ません**。

最終的な状態は次のとおりです。ユーザーが `brew install foo` を実行すると、`foo` に対応するボトルは、そのボトルの*アテステーション*に対して定義された有効な署名がある*場合に、かつその場合にかぎり*、インストールされます。そして、その署名は、暗号学的に有効であり、*かつ*、`foo` がビルドされた tap のリポジトリのアイデンティティ（たとえば `homebrew/homebrew-core`）に対応している*場合に、かつその場合にかぎり*、有効とみなされます。

### 攻撃者のモデル {#attacker-models}

下に挙げる攻撃者のモデルは、すべてリモートのモデルです。ローカルの攻撃者はモデル化していません。ファイルを変更したりコードを実行したりできるローカルの攻撃者はすでに勝っている、という Homebrew の従来からの運用上の前提に従っているためです。この前提は、Web PKI におけるクライアントの完全性の前提（つまり、クライアントの信頼の基点そのものは侵害されていないという前提）に相当します。

これらのモデルは、網羅的であることを意図したものではありません。

#### モデル 1: ボトルのストレージの侵害 {#model-1-compromise-of-bottle-storage}

**シナリオ**: Mallory は、Homebrew の通常のボトルのビルドと公開のワークフローを迂回でき、悪意のあるボトルを tap のボトルのストレージへアップロードできます。

**緩和策**: ボトルのストレージへのアップロードの権限*だけ*では、Mallory は自分の悪意のあるボトルに対する有効な署名を偽造できません。`brew install $compromised-bottle` は、署名がないか一致しないためにインストールに失敗し、`$compromised-bottle` をインストールしようとしたユーザーには、はっきりと目立つ形で通知されます。

**結果**: Mallory は、侵害されたボトルのインストールを強制**できません**。Mallory は検知されないままです。

#### モデル 2: ボトルをビルドするワークフローの侵害 {#model-2-compromise-of-bottle-building-workflows}

**シナリオ**: Mallory は、Homebrew の正規のボトルのビルドのワークフローに割り込むか、そのほかの方法で制御できます。彼女は、自分の存在を明かさない方法で、正規のボトルを改変したり、悪意のあるボトルに丸ごと置き換えたりできます。

**緩和策**: ボトルをビルドするワークフローへのアクセス*だけ*では、Mallory は依然として署名のワークフローにアクセスできません。そのため、彼女は自分の悪意のあるボトルに対する有効な署名を無理に作らせることができず、上で説明したとおり、悪意のあるボトルのインストールを強いることは依然としてできません。

**結果**: Mallory は、侵害されたボトルのインストールを強制**できません**。Mallory は検知されないままです。

#### モデル 3: ボトルに署名するワークフローの侵害 {#model-3-compromise-of-bottle-signing-workflows}

**シナリオ**: Mallory は、Homebrew の正規のボトルの署名のワークフローに割り込むか、そのほかの方法で制御できます。彼女は、自分が管理する悪意のあるボトルに署名でき、その結果、ある tap の署名のアイデンティティには一致するものの正規ではない署名ができあがります。

**緩和策**: ボトルに署名するワークフローへのアクセス*だけ*では、Mallory は、不正に署名した自分のボトルをボトルのストレージへアップロードできません。彼女のボトルは署名検証には通る*はず*ですが、ユーザーの手には届かないままです。Sigstore の透明性サービスがあるため、Mallory はこの攻撃を仕掛けることで隠密性を失います。

**結果**: Mallory は、侵害されたボトルのインストールを強制**できません**。Mallory は検知されないままでは**いられません**。

#### モデル 4: ボトルをビルドするワークフロー*と*ボトルに署名するワークフローの侵害 {#model-4-compromise-of-bottle-building-and-bottle-signing-workflows}

**シナリオ**: Mallory は、ボトルのビルドのワークフローと署名のワークフローの両方を侵害でき、ボトルを作り、不正に署名し、ボトルのストレージへアップロードできます。

**緩和策**: Mallory のボトルは正規のものに見え、配布もされているので、彼女はユーザーに `brew install $compromised-bottle` を実行させることに成功します。しかし、それには代償が伴います。彼女は Sigstore の透明性サービスによって隠密性を失い、Homebrew のボトル配布の仕組みのために、侵害したボトルを*すべての*ユーザーに配布せざるをえません。

**結果**: Mallory は、侵害されたボトルのインストールを強制**できます**。Mallory は検知されないままでは**いられず**、個々のユーザーを狙うこともできません。

### まとめ {#summary-1}

モデル (1)、(2)、(3) では、Mallory は、悪意をもって改変したボトルをユーザーにインストールさせることが**できません**。これは、それらのボトルに対して、有効だが正規ではない署名を別途生成できる場合（3 つ目のシナリオ）でも同じです。

モデル (1) と (2) では、Mallory は、透明性ログという意味では「検知されない」ままです。彼女はほかの手段（イベントログやセキュリティ監視システムなど）で検知されるかもしれません。しかし、有効だが正規ではない署名を生成できないということは、透明性ログには彼女の攻撃について対処につながる証拠が残らないということです。検知されないこと*自体*は、Mallory にとって成功した「勝ち」の状態ではありません。

モデル (3) と (4) では、Mallory は、隠密性を失うことと引き換えに、正規ではない署名を生成できます。これは、Mallory が正規ではない署名を送信せざるをえない透明性サービスを、Homebrew やほかの関係者が監視していることを前提にしています。

モデル (4)（「最悪の場合」）では、Mallory は、悪意のある、不正に署名されたボトルをユーザーにインストールさせることが**できます**。しかし、この場合でも、Mallory の攻撃の態勢は弱まっています。彼女は、攻撃を仕掛けることと引き換えに隠密性を失うことを受け入れざるをえず、個々のユーザーを狙うこともできません。攻撃者にとってのリスクという点で、これは Web PKI のもとでの Certificate Transparency に相当します。
